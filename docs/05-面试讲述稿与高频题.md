# 05 面试讲述稿与高频题

> 本文件解决"项目做了但讲不出来"的问题。包含：项目讲述稿（2 分钟 / 5 分钟）、高频面试题答题框架、反问面试官清单、简历项目描述写法。

## 一、项目讲述稿

### 1.1 2 分钟版（自我介绍里带过）

> "为了补齐云售后技术支持的实操短板，我自建了一套三层的云上业务故障演练环境，把云厂商售后最常见的高频故障——比如接入层 502/504、连接池耗尽、慢 SQL、容器 OOMKilled 等——逐一复现，并对每个故障留存了指标、日志和复盘报告。
>
> 这个项目让我形成了一套固定的排障方法：先看网关 5xx 和到达率判断是不是'服务不可达'，再看后端资源判断是不是'服务处理不了'，然后按接入层→应用层→数据层→缓存层→节点层逐层二分定位。比如在健康检查失败那个场景里，用户全 502，但后端 CPU、内存、数据库全都正常——这时候就不能在业务逻辑里打转，而是直接回到接入层检查健康检查和安全组配置。
>
> 我还会把每个故障沉淀成一条告警规则和一条知识库条目，让下次故障在客户报障之前就被发现。"

### 1.2 5 分钟版（STAR 结构，主讲一个招牌案例）

**S（背景）**
> "云售后技术支持岗最看重的是'能不能快速定位并恢复'。我没有生产环境，所以自建了一套可运行的仿真三层业务环境，覆盖接入/应用/数据/缓存/节点五个故障域。"

**T（任务）**
> "目标是：对每一类高频故障，能说清现象、能给出排障路径、能量化影响、能写出 RCA，并能把它变成一条永久告警。"

**A（行动）——主讲 S5 健康检查失败（二阶问题）**
> "最典型的是健康检查失败导致的 502/504。现象是用户侧全部 502/504，网关的 upstream 5xx 累计新增了 7000 多次，业务接口到达率从 118 掉到 60 —— 说明后端被摘除了。但关键在于：后端实例的 CPU、内存、数据库指标全部正常。
>
> 这个'网关 5xx 高但后端资源正常'的分叉，直接告诉我问题不在业务代码，而在接入层。于是我去直连后端验证 /healthz 实际返回码，发现健康检查探针返回 500，SLB 把后端标记 DOWN 并摘除，网关因为没有可用后端就返回了 502；日志里能直接看到 `no live upstreams` 和 `upstream timed out` 504。
>
> 止损动作是：核对并修正健康检查配置，检查安全组规则，把 /healthz 修为真实反映服务状态。"

**R（结果）**
> "最终形成了：一份 RCA 复盘报告、一条'网关 5xx 突增 + 到达率骤降'的告警规则、一条知识库条目。整个项目的 8 个场景我都留存了实测的指标、日志和时间线。"

## 二、高频面试题与答题框架

> 售后技术支持面试通常分：基础技术（Linux/网络/云产品/DB/容器）、排障思维（给一个现象让你分析）、行为与沟通。以下按类给出答题骨架。

### 2.1 基础技术

**Q：Linux 上发现 CPU 很高，你怎么排查？**
> 框架：`top` 看整体负载与进程 → `top -H` / `pidstat` 定位到线程 → 判断是用户态（应用热点）还是内核态（sys 高，系统调用/IO）→ `perf`/火焰图定位函数 → 区分"应用自己吃 CPU"和"被同机其他进程挤占 / CPU steal（超卖）"。

**Q：磁盘满了怎么办？**
> 关键点：**空间和 inode 都要看**（`df -h` 和 `df -i`）→ `du`/`find` 定位大文件与小文件 → 常见元凶是未轮转的日志、核心转储、临时文件 → 立即清理并配置 `logrotate` → 注意 `lsof | grep deleted`（文件被删但句柄未释放，空间不回收，需重启进程）。

**Q：一个服务突然 5xx，你怎么分层定位？**
> 框架：先看**网关 5xx + 到达率**（服务是否可达）→ 再看**后端资源**（服务是否能处理）→ 一致则往下（应用→DB→缓存→节点），不一致则往上（接入层/配置）。这是本项目的核心方法论。

**Q：DNS 解析慢/失败如何排查？**
> `dig/nslookup` 指定 nameserver 复现 → 检查 `/etc/resolv.conf` 的 timeout/attempts → 高峰期并发可能打爆 DNS → K8s 看 CoreDNS 状态与日志 → 应用侧加本地缓存与重试。

### 2.2 网络与接入层

**Q：502 和 504 的区别？**
> `502 Bad Gateway`：网关从上游收到**无效响应**（后端拒绝连接/无可用后端/协议错）；`504 Gateway Timeout`：网关**等上游超时**。两者都可能源于后端摘除、后端过慢、健康检查失败。

**Q：负载均衡的健康检查你会怎么配？注意什么？**
> 要点：健康检查路径要能**真实反映服务状态**（`/healthz` 别只返回 200）→ 间隔/超时/阈值要避免"偶发抖动被摘除"→ 检查来源 IP 与端口要在安全组放通 → 健康检查失败要**独立告警**，避免和业务故障混淆。

### 2.3 数据库

**Q：数据库 CPU 突然很高怎么处理？**
> 先看**TOP SQL / 慢查询**（是单条慢还是整体 QPS 高）→ 用 `EXPLAIN` 看是否**全表扫描 / 索引失效**（隐式类型转换、函数包裹字段）→ 应急：加只读实例、加索引、限流、缓存兜底；根因：SQL 治理 + 上线审核。

**Q：应用报 `Connection is not available` 怎么办？**
> 判断连接池是否被打满（`active == total`）→ 是否有**连接泄漏**（`checked out & never returned`，用 `leakDetectionThreshold` 定位）→ 还是**慢调用长期占用**连接 → 止损重启 + 扩池，注意 `实例数×池大小 ≤ DB 最大连接数`。

### 2.4 容器与 K8s

**Q：Pod 一直重启怎么排查？**
> `kubectl describe pod` 看 `Last State` 与**退出码**（137=OOMKilled，143=SIGTERM）→ `kubectl logs --previous` 看崩溃前日志 → OOM 则看内存 limit 与内存曲线 → CrashLoopBackOff 看应用启动日志/配置/依赖。

**Q：OOMKilled 是节点内存不足还是容器内存超限？**
> 容器 `exit 137` + limit 超限是**容器级**；节点内存不足会有**驱逐（Evicted）** 事件。两者处置不同：前者优化应用/调 limit，后者看节点容量与多容器争抢。

### 2.5 行为与沟通类

**Q：客户很着急、一直催，你怎么处理？**
> 先**给预期**（"X 分钟内第一次反馈"），再**给进展**（每 15–30 分钟同步），**给规避方案**（临时缓解），最后**给交付物**（RCA 报告）。原则：先止损、后根因；沟通频率本身就能降低焦虑。

**Q：如何处理一个你暂时无法定位的问题？**
> 分层排除并**明确已排除的方向**，把范围收敛到具体层；同时**升级二线**、向客户**要关键信息**（日志/时间点/复现方式），保持接口人角色。

**Q：一次故障之后你会做什么？**
> 产出一份 **RCA**（时间线 + 5 Whys 根因 + 改进项），并把结论**转化为告警规则或知识库条目**，使同类故障可被自动发现。

## 四、简历项目描述写法

> 放在"项目经历"里，用**动词 + 技术 + 量化结果**，避免空泛。

**推荐写法：**

```
云上业务稳定性保障与故障处置实战（个人项目）
- 自建三层云上业务仿真环境（接入/应用/数据/缓存/节点），复现 8 类高频故障：
  健康检查失败 502/504、连接池耗尽、慢 SQL、容器 OOMKilled、磁盘/inode 打满、DNS 异常、热 key 等。
- 建立"网关 5xx + 到达率 → 后端资源"的分层定位法，将故障域从 5 层快速收敛；
  实测定位健康检查失败场景（后端资源正常但网关 5xx 新增 7000+）。
- 为 8 个场景产出 RCA 复盘报告与 13 条 Prometheus 告警规则 + 告警抑制配置，
  实现"一次故障 → 一条永久告警 + 一条知识库条目"的闭环。
- 技术栈：Linux、TCP/DNS、Nginx/SLB、MySQL、Redis、Docker/K8s、Prometheus/Alertmanager/Grafana、Python。
```

**避免的写法**："熟悉云计算、了解 Linux、有一定的排障能力" —— 全是形容词，没有证据。
