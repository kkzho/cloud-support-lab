# 04 稳定性治理方案

> 技术支持工程师的价值不只在"救火"，更在"把火扑灭在起火之前"。本文件说明如何把演练中发现的问题，转化为一套可落地的稳定性治理方案，对应云厂商"架构优化 / 稳定性服务"类工作。

---

## 一、目标：用 SLI / SLO / 错误预算管理稳定性

| 概念 | 本项目的取值 | 说明 |
|---|---|---|
| **SLI**（指标） | 可用性 = 成功请求 / 总请求；延迟 = P99 | 可测量 |
| **SLO**（目标） | 月度可用性 ≥ 99.9%；P99 ≤ 300ms | 一个可承诺的目标 |
| **错误预算** | 100% − SLO = 0.1%/月 ≈ 43 分钟 | 预算内可放行变更，超支则冻结发布 |
| **告警策略** | 基于**错误预算消耗速率**（burn rate）多窗口告警 | 避免"报警太多等于没报警" |

> 一句话："不看单点阈值，看**预算烧得多快**。"这是现代 SRE 告警与传统阈值告警的核心区别，也是面试加分点。

---

## 二、高可用设计（对应本项目的脆弱点）

| 演练暴露的问题 | 目标架构改造 |
|---|---|
| S5 健康检查失败即全站不可用 | SLB **多可用区** + 后端**跨可用区**部署 + 健康检查契约化 |
| S1 CPU 饱和无弹性 | 应用**无状态化 + ≥2 实例 + HPA 自动伸缩** |
| S3 慢 SQL 拖垮 DB | RDS **主备/多可用区** + **只读实例**分流读 + 慢查询治理 |
| S4 单实例 OOM 影响面大 | 多实例 + 就绪/存活探针 + 优雅摘除 |
| S7 强依赖 DNS | 多 nameserver + 本地缓存 + 必要依赖直连/服务发现 |
| 单可用区故障 | 关键业务**跨可用区/跨 Region** 容灾 |

**冗余原则**：任何一个**单点**（单实例、单可用区、单数据中心、单 DNS）都不应成为"全站开关"。

---

## 三、监控告警体系

### 3.1 分层监控（黄金四指标）

| 层次 | 指标 | 本项目 |
|---|---|---|
| 流量 | QPS、5xx 率、到达率 | `http_requests_total`、`gateway_upstream_5xx_total` |
| 错误 | 错误率、错误码分布 | 5xx 率 |
| 延迟 | P50/P95/P99 | `http_request_duration_ms_*` |
| 饱和 | CPU/内存/连接/磁盘 | `node_*`、`app_conn_pool_*`、`db_*` |

### 3.2 告警工程（本项目已配置）

- 每条告警包含：**条件 + 持续时间(`for`) + 严重度(`severity`) + 摘要 + 排障提示**；
  见 [../ops/prometheus/rules.yml](../ops/prometheus/rules.yml)（13 条规则，覆盖 8 个场景）；
- **告警抑制**：上游告警抑制下游衍生告警，防止"告警风暴"；
  见 [../ops/alertmanager/alertmanager.yml](../ops/alertmanager/alertmanager.yml)（`inhibit_rules` + `group_by`）；
- 可视化看板：见 [../ops/grafana/dashboard.json](../ops/grafana/dashboard.json)（12 个面板，覆盖流量/延迟/连接池/DB/节点/缓存/重启）。

### 3.3 告警设计的三条反模式（面试可讲）

1. **只报警不指向动作**：告警描述里必须带"看什么、查哪里"（本项目的 `description` 已带排障提示）；
2. **阈值拍脑袋**：阈值应来自容量基线与错误预算，而非固定 80%；
3. **无抑制**：一次底层故障会引爆几十条衍生告警，必须用抑制规则收敛。

## 四、容量规划

- **基线法**：以压测确定单实例容量（本项目稳定态：P99 ≈ 200ms、连接池 6/10、DB CPU 22%）；
- **水位法**：设定安全水位（CPU/内存/磁盘/inode < 80%），超过即扩容或告警；
- **弹性法**：按业务峰谷（如大促）配置自动伸缩规则与预热；
- **连接数守恒**：`实例数 × 单实例连接池 ≤ DB 最大连接数`（S2 的根因之一）。

---

## 五、变更与发布治理（大多数故障的真正来源）

- **发布**：灰度 + 分批 + 可回滚；S3、S5 这类故障常由变更引入；
- **变更窗口**：重大变更避开业务高峰；变更前生成回滚预案；
- **配置即代码**：安全组、健康检查等配置纳入版本管理（避免"误删规则"如 S5）；
- **变更后观察期**：发布后固定观察核心 SLI 一段时间。

---

## 六、容灾、快恢与降级预案

| 预案类型 | 做法 | 本项目对应 |
|---|---|---|
| 快恢 | 一键回滚、快速重建实例 | S1/S2 重启、S3 回滚 |
| 降级 | 非核心功能可关闭、可降级 | S3 缓存兜底、S1 限流 |
| 容灾 | 跨可用区/跨 Region 切换 | 架构改造目标 |
| 数据保护 | 备份 + 快照 + 定期恢复演练 | DB/云盘 |

**预案三要素**：谁触发、执行哪一步、如何验证恢复。演练要像消防演习一样定期做（本项目就是一次完整的"演习"）。

---

## 七、成本与稳定性的平衡

- 默认**多副本**会带来成本，需按业务等级分级（核心业务多可用区，非核心可接受单可用区）；
- 用**自动伸缩**替代长期超配；
- 用**错误预算**决定"该不该为稳定性继续加投入"。

---

## 八、把本项目作为"稳定性服务"的交付模板

给客户（或面试官）讲这套方案时的推荐结构：

```
现状评估(演练暴露的脆弱点) → 风险清单 → 改造方案(高可用/监控/变更/容灾) →
落地优先级(先止损类、再治理类) → 验收标准(SLO/告警生效) → 持续运营(演练常态化)
```
