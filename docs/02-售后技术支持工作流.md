# 02 售后技术支持工作流

> 本文件把"售后技术支持"从"接电话解决问题"升级为一套**可复制的服务流程**：受理 → 分级 → 定位 → 止损 → 根因 → 修复 → 复盘 → 沉淀。这也是云厂商技术支持岗真正的日常工作方式。

---

## 一、工单来源与受理

| 来源 | 特点 | 首响要求 |
|---|---|---|
| 工单系统 | 有完整上下文、可留痕 | 按规定 SLA |
| 电话 | 紧急、P0/P1 居多 | 立即接起，边沟通边建单 |
| IM 群（企业微信群/工单群） | 客户与厂商混群、信息碎片化 | 快速认领并"接单"话术 |
| 邮件 | 正式、含附件与截图 | 按 SLA |

**受理三件事（缺一不可）**：
1. **确认影响面**：多少用户、哪些业务、是否还在持续；
2. **确认时间线**：故障开始时间、是否伴随变更（发布、配置变更、扩容）；
3. **建单并回执**：给客户一个工单号与预计响应时间。

---

## 二、工单分级与 SLA

| 级别 | 判定标准 | 首响 | 处置目标 | 升级 |
|---|---|---|---|---|
| **P0** | 核心业务全量不可用 / 数据丢失风险 | ≤ 5 分钟 | 立即拉起 war room，2 小时内止损 | 立即升级至二线 + 值班经理 |
| **P1** | 核心功能大面积受损 / 性能严重劣化 | ≤ 15 分钟 | 4 小时内恢复或给出规避方案 | 30 分钟内升级二线 |
| **P2** | 部分功能异常 / 单实例问题 | ≤ 30 分钟 | 1 个工作日内处置 | 视情况升级 |
| **P3** | 咨询、配置协助、轻微异常 | ≤ 4 小时 | 3 个工作日内答复 | 不升级 |

> SLA 数字是岗位面试里最常见的考点之一。落地时以**厂商实际 SLA 为准**，本表用于体现"分级思维"。

---

## 三、核心排障方法论：七步法

```
① 现象确认 → ② 影响面评估 → ③ 假设与分层 → ④ 并行验证 → ⑤ 止损 → ⑥ 根因定位 → ⑦ 复盘预防
```

1. **现象确认**：把客户的主观描述（"打不开""很慢"）翻译成客观指标（5xx 率、P99、错误码、时间点）。
2. **影响面评估**：全量还是部分？持续还是间歇？有无规律（如整点、发布后）？
3. **假设与分层**：按 [01 文档](01-架构与云产品映射.md) 的五个故障域提出假设，**从接入层往下逐层排除**。
4. **并行验证**：同时取"网关指标 + 后端资源指标 + 应用日志 + 依赖服务"。一个关键判断点是：**网关 5xx 高 vs 后端资源是否也异常**——两者不一致，问题基本锁定在接入层或配置。
5. **止损优先**：排障与止损并行。可用手段：回滚变更、扩容、限流、切流、重启、加白名单。
6. **根因定位**：用"5 Whys"追问到可修复的根因，而不是停在"重启后恢复了"。
7. **复盘预防**：沉淀为 RCA + 告警规则 + 知识库条目（见第七节）。

**止损与根因的优先级原则**：客户在故障中要的是"恢复"，不是"原因"。**先止损、再根因**；但止损动作要可回滚、并记录，避免制造第二个故障。

## 四、客户沟通话术

沟通的目标是**降低客户焦虑 + 建立可控预期**，而不是暴露内部混乱。

**认领/首响：**
> "您好，工单已受理，编号 #xxxxx。我们已经在处理，预计 X 分钟内给您第一次反馈。"

**阶段性同步（P0/P1 每 15–30 分钟）：**
> "当前已确认影响范围是 XX；我们已在做 XX（止损动作），预计在 XX 时间点给您下一步结论。目前业务侧可先通过 XX 临时规避。"

**无法立即定位时：**
> "初步排除 A、B 两个方向，目前聚焦在 C。需要您协助提供 XX（日志/时间点/复现方式），拿到后我这边优先跟进。"

**升级/需协调时：**
> "这个问题已升级到产品/研发二线，由 X 同学协同处理，我作为您的主要接口人保持同步。"

**恢复后：**
> "业务已恢复，我们会在 X 个工作日内提供一份正式的故障复盘报告（RCA），包含时间线、根因与改进项。"

> 话术模板见 [tickets/工单模板与话术.md](../tickets/工单模板与话术.md)。

## 五、升级与协同机制

- **一线 → 二线**：一线负责受理、现象确认、止损与常规排障；当确认是产品缺陷、需改配置/改代码、或超出 SOP 时升级二线。
- **二线 → 研发/产品**：能复现的缺陷、需要发版修复的问题，提缺陷单并跟进。
- **重大故障（P0/P1）**：拉起 war room，明确三个角色：**指挥（协调）**、**执行（操作）**、**记录（时间线）**。记录者要独立于操作者——这是很多团队复盘质量差的原因：没人专心记时间线。

---

## 六、关键服务指标（Service Metrics）

| 指标 | 含义 | 为什么重要 |
|---|---|---|
| 首响时长 | 从客户提出到第一次有效响应 | 客户满意度的第一决定因素 |
| 一次解决率 (FCR) | 一次性解决、无需反复的工单占比 | 体现 SOP 与知识库质量 |
| SLA 达成率 | 按时首响/按时处置的比例 | 履约能力 |
| 平均修复时长 (MTTR) | 从故障发生到恢复 | 稳定性核心指标 |
| 工单返工率 / 升级率 | 升级到二线的占比 | 一线能力水位 |
| CSAT | 客户满意度 | 结果指标 |

## 七、复盘（RCA / Postmortem）机制

**触发条件**：P0/P1 故障、任何影响客户业务的变更事故，必须产出 RCA。

**RCA 必备要素**：
1. 事件概要（一句话说清"谁、在何时、受什么影响、多久"）；
2. **时间线**（精确到分钟，含发现、止损、恢复、升级节点）；
3. 影响面（受影响业务、用户量、时长）；
4. 根因（用 5 Whys 追到可修复层）；
5. 处置过程与止损动作；
6. **改进项（Action Items）**：每条都有负责人、截止时间、验收方式；
7. 客户沟通纪要。

**复盘三原则**：
- **对事不对人**（Blameless）：目标是修复系统，不是追责；
- **可验证**：每条改进项都要能验收；
- **可沉淀**：结论必须转成告警规则或知识库条目，否则下次还会再犯。

RCA 样例见 [rca/](rca/)。

## 八、知识库沉淀

每一次解决完的问题，都应产出/更新一条知识库条目，格式统一：

```
【现象】...
【适用产品/版本】...
【快速判断】看哪几个指标/日志关键词
【根因】...
【处置步骤】1..2..3..
【预防/关联告警】...
```

> 知识库条目样例见 [tickets/知识库-KB示例.md](../tickets/知识库-KB示例.md)。

## 九、把一次故障变成一条永久告警（本项目的闭环）

以 S5（健康检查失败导致 502/504）为例，闭环链路：

```
客户报障 → 排障定位(接入层) → 止损(修健康检查配置) → RCA → 新增告警规则 →
ops/prometheus/rules.yml 中出现 “健康检查失败/网关 5xx 突增” 规则 →
下一次同类故障在客户报障前就被自动发现
```

见 [../ops/prometheus/rules.yml](../ops/prometheus/rules.yml) 与 [../ops/alertmanager/alertmanager.yml](../ops/alertmanager/alertmanager.yml)。
