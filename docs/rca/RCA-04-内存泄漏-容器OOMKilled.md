---

## 一、事件概要

服务每隔一段时间就重启一次，重启窗口内出现少量 5xx。排查发现应用存在**内存泄漏**，RSS 持续增长超过容器 limit，被内核 **OOMKilled**（exit code 137），容器反复重启，内存曲线呈**锯齿状**。由于 5xx 率很低（0.25%），初期容易被误判为"偶发抖动"而**漏排**。

---

## 二、影响面

| 维度 | 实测 |
|---|---|
| 资源 | `node_mem_percent` 峰值 **99.8%**（均值 66.4%），呈锯齿 |
| 稳定性 | 容器重启次数故障期新增 **3 次** |
| 用户侧 | 重启瞬间少量 5xx（`http_5xx_rate = 0.25%`），网关 upstream 5xx 新增 **45** |
| 隐性风险 | 重启导致容量不稳定；若实例少，重启窗口内可能真正不可用 |

## 四、根因分析（5 Whys）

1. **为什么服务周期性重启？** → 容器被内核杀死后自动重启。
2. **为什么被杀死？** → 内存使用超过容器 limit，触发 OOMKilled（exit 137）。
3. **为什么内存会超过 limit？** → 应用内存持续增长（锯齿上升段），未自然回落。
4. **为什么内存持续增长？** → 存在**内存泄漏**（缓存/监听器/大对象无上限增长）。
5. **（根因层）为什么没提前发现？** → 未监控**容器内存水位与重启次数**，且 limit 设定未基于压测峰值。

**根因（可修复层）**：应用存在内存泄漏，RSS 持续增长超过容器 limit 触发 OOMKilled。

---

## 五、处置过程

| 步骤 | 动作 | 效果 |
|---|---|---|
| 1. 现象确认 | 客户报"服务每隔一段时间重启一次" | 判定为稳定性问题 |
| 2. 关键证据 | `kubectl describe pod` 看到 `Last State: OOMKilled / exit 137`；`--previous` 日志 | 确认 OOMKilled |
| 3. 判定方向 | 内存曲线锯齿 + 无自然回落 | 判定为**内存泄漏**（而非 limit 过小） |
| 4. 止损 | 临时抬高内存 limit / 扩容；多实例时先摘除异常实例 | 停止周期性抖动 |
| 5. 根因修复 | heap dump 分析泄漏对象与引用链并修复 | 内存曲线平稳 |

## 八、复盘结论

- **教训**：低 5xx 率的"偶发重启"最容易被漏排；**退出码 137 + 内存曲线锯齿**是识别 OOMKilled 内存泄漏的关键证据。
- **沉淀**：告警规则（容器内存水位 + 重启次数）+ 知识库条目 KB-004。
