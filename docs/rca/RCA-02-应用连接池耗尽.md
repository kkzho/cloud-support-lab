# RCA-02 应用数据库连接池耗尽

| 项目 | 内容 |
|---|---|
| 事件编号 | RCA-2026-0112-02 |
| 严重级别 | P1（大面积接口失败） |
| 影响组件 | 应用层（连接池 / 连接泄漏） |
| 发生时间 | 2026-01-12 09:00:40 |
| 恢复时间 | 2026-01-12 09:02:50（演练时间轴） |
| 演练场景 | `evidence/S2-conn-pool-exhaustion/` |

---

## 一、事件概要

应用大面积返回 5xx，错误信息为 `Connection is not available`。排查发现**数据库本身健康**（CPU 22%、连接数正常），问题出在**应用侧数据库连接池被占满**，且日志明确显示存在**连接泄漏**（获取的连接未归还）。这是典型的"**故障在应用层、却通过数据库表象暴露**"的问题。

---

## 二、影响面

| 维度 | 实测 |
|---|---|
| 用户侧错误 | 5xx 错误率达 **20.5%**，故障期网关 upstream 5xx 新增 **3,163** |
| 延迟 | P99 从 ~199ms 恶化到 **422ms** |
| 连接池 | `app_conn_pool_in_use = 10 / 10`（**打满**） |
| 数据库 | `db_connections_used ≈ 3`、CPU 22% —— **正常** |

---

## 三、时间线（实测日志）

| 时间 | 事件 |
|---|---|
| 09:00:40 | 首次出现 `WARN connection leak detected: 10/10 connections checked out and never returned to HikariPool-1` |
| 09:00:40 | 首次出现 `ERROR HikariPool-1 - Connection is not available, request timed out after 400ms (total=10, active=10, idle=0, waiting=23)` |
| 09:00:40–09:02:50 | 连接池持续 10/10 打满，等待队列不断增长（waiting 一度达 36），5xx 持续 |
| 09:02:50 | 应用重启释放连接后，连接池回落，业务恢复 |

> 取自 `evidence/S2-conn-pool-exhaustion/app.log` 与 `summary.json`。

---

## 四、根因分析（5 Whys）

1. **为什么大量接口 5xx？** → 请求拿不到数据库连接而超时。
2. **为什么拿不到连接？** → 连接池内 10 个连接全被占用（`active=10, idle=0`）。
3. **为什么全被占用？** → 存在**连接泄漏**：代码在异常路径下未归还连接（日志 `checked out and never returned`）。
4. **为什么没有被及时发现？** → 连接池未开启 `leakDetectionThreshold`，泄漏在早期无法被观测。
5. **（根因层）为什么泄漏会积累到打满？** → 连接获取/归还未强制使用 try-with-resources / finally，缺乏代码级约束与静态检查。

**根因（可修复层）**：应用存在连接泄漏，连接池被逐步占满，导致后续请求等待超时并大量失败。

---

## 五、处置过程

| 步骤 | 动作 | 效果 |
|---|---|---|
| 1. 现象确认 | 客户报大量 `Connection is not available` | 判定为应用侧错误 |
| 2. 关键分叉 | 核对 DB 侧：CPU 22%、连接数正常 | **锁定问题在应用连接池** |
| 3. 证据定位 | 检索日志，命中 `connection leak detected` | 确认存在**连接泄漏** |
| 4. 止损 | 滚动重启实例，临时扩大 `maximumPoolSize`、缩短 `connectionTimeout` | 连接释放，业务恢复 |
| 5. 根因修复 | 开启泄漏检测，定位未归还连接的代码路径并修复 | 泄漏消除 |

---

## 六、改进项（Action Items）

| # | 改进项 | 优先级 | 验收标准 |
|---|---|---|---|
| 1 | 修复连接泄漏（try-with-resources / finally 归还） | 高 | 压测下 `active` 不再单调增长 |
| 2 | 开启 `leakDetectionThreshold` 并接入告警 | 高 | 泄漏超阈值即告警 |
| 3 | 复核连接池参数：`实例数 × 池大小 ≤ DB 最大连接数` | 高 | 参数文档化并通过容量评估 |
| 4 | 告警：`conn_pool_in_use / conn_pool_size > 0.8` 持续 2 分钟 | 高 | 已在 `ops/prometheus/rules.yml` 落地 |
| 5 | 静态扫描禁止裸获取连接 | 中 | CI 拦截 |

## 八、复盘结论

- **教训**：DB 报错未必是 DB 的问题；**连接池指标 + 应用日志**是区分"DB 故障"和"应用连接管理故障"的关键。
- **沉淀**：告警规则（连接池水位）+ 知识库条目 KB-002，把"等客户报障"变为"连接池打满即告警"。
