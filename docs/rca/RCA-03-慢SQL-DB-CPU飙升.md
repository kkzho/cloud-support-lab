---

## 一、事件概要

业务接口 P99 进入**秒级**，数据库 CPU 逼近 100%，慢查询大量堆积。根因为**新上线的查询走了缺失索引的 SQL**，产生全表扫描，DB CPU 被打满，并**连带占满应用连接池**，形成"数据库瓶颈 → 应用排队 → 用户 5xx"的放大链路。

---

## 二、影响面

| 维度 | 实测 |
|---|---|
| 用户侧错误 | 5xx 达 **15.7%**，网关 upstream 5xx 新增 **2,436** |
| 延迟 | P99 从 199ms 恶化到 **2,028ms**（峰值 3,406ms） |
| 数据库 | `db_cpu_percent` **22% → 95.4%**；慢查询故障期新增 **364** 次 |
| 次级影响 | 连接池被慢查询占用至 **10/10**，`db_connections_used` 升高 |

## 四、根因分析（5 Whys）

1. **为什么接口 P99 秒级？** → 请求在数据库层排队等待慢查询完成。
2. **为什么有慢查询？** → 查询 `... WHERE o.status=?` 的 `rows_examined` 达百万级，属**全表扫描**。
3. **为什么全表扫描？** → 该查询**缺少可用索引**（或索引失效，如 WHERE 条件未命中索引列）。
4. **为什么缺少索引？** → 新上线接口的 SQL 未经索引评审。
5. **（根因层）为什么没在上线前拦住？** → 缺**上线 SQL 审核与索引基线**机制。

**根因（可修复层）**：新上线查询缺失索引导致全表扫描，DB CPU 被打满，并连带占满应用连接池。

---

## 五、处置过程

| 步骤 | 动作 | 效果 |
|---|---|---|
| 1. 现象确认 | 接口 P99 秒级 + DB CPU 打满 | 判定为数据层瓶颈 |
| 2. 定位 TOP SQL | 从慢查询日志提取具体 SQL 与 `rows_examined` | 锁定问题 SQL |
| 3. 验证 | `EXPLAIN` 确认全表扫描（type=ALL / 未命中索引） | 确认根因方向 |
| 4. 止损 | 应急加索引 / 改写 SQL；加只读实例分流；缓存兜底 | DB CPU 回落，P99 恢复 |
| 5. 变更处置 | 评估是否回滚引入该 SQL 的发布 | 防止再次引入 |

---

## 六、改进项（Action Items）

| # | 改进项 | 优先级 | 验收标准 |
|---|---|---|---|
| 1 | 为问题 SQL 建索引（评估写入影响）或改写为命中索引的形式 | 高 | `EXPLAIN` 的 `rows` 大幅下降 |
| 2 | 建立**上线 SQL 审核**与核心表索引基线 | 高 | 新 SQL 上线前必经评审 |
| 3 | 只读实例分流读流量，读写分离 | 高 | 读流量不压主库 CPU |
| 4 | 告警：`db_cpu_percent > 80%` 持续 5 分钟；慢查询增速突增 | 高 | 已在 `ops/prometheus/rules.yml` 落地 |
| 5 | 应用侧对重查询加缓存/降级 | 中 | 缓存命中率提升，DB 压力下降 |

## 八、复盘结论

- **教训**：数据库瓶颈会**向下游传导**（连接池、接口延迟），必须区分"DB 自身故障"与"应用 SQL 拖垮 DB"。
