# RCA-01 负载均衡健康检查失败导致 502/504

| 项目 | 内容 |
|---|---|
| 事件编号 | RCA-2026-0112-01 |
| 严重级别 | P1（核心链路大面积不可用） |
| 影响组件 | 接入层（SLB / 健康检查 / 安全组） |
| 发生时间 | 2026-01-12 09:00:54 |
| 恢复时间 | 2026-01-12 09:02:40 |
| 持续时长 | 约 106 s（演练环境时间轴） |
| 演练场景 | `evidence/S5-lb-healthcheck-5xx/` |

---

## 一、事件概要

业务接口在用户侧出现**大面积 502/504**，但后端应用实例的 CPU、内存、数据库指标**全部正常**。经排查，根因为**负载均衡健康检查探针持续失败**，后端实例被判定 DOWN 并摘除，网关在"无可用后端"时返回 502/504。本事件是典型的"**二阶问题**"——现象出现在接入层，而问题**不在**业务逻辑。

---

## 二、影响面

| 维度 | 实测 |
|---|---|
| 用户侧错误 | 网关 upstream 5xx 故障期新增 **7,097** 次 |
| 可用容量 | 业务接口到达率从 **118 req/s → 60 req/s**（后端被摘除） |
| 后端资源 | CPU 25%、内存 42%、DB CPU 22%、连接池 3.6/10 —— **均正常** |
| 业务影响 | 大面积不可用或严重降级 |

---

## 三、时间线（实测）

| 时间 | 事件 |
|---|---|
| 09:00:40 | 触发点：后端 `/healthz` 因配置/依赖问题开始返回 500（演练注入） |
| 09:00:55 | SLB 首次健康检查失败：`health check failed for backend 10.0.0.21:8080 GET /healthz -> HTTP 500, backend marked DOWN` |
| 09:00:58 | 网关出现首个 504：`upstream timed out (110) client ... status=504, request: GET /api/order/list` |
| 09:01:00 | 网关出现首个 502：`no live upstreams while connecting to upstream, status=502` |
| 09:01:00–09:02:40 | 后端持续被判定 DOWN，业务接口到达率维持低位（~60），网关持续 502/504 |
| 09:02:40 | 修正健康检查配置后，后端恢复健康，流量回归（到达率回到 ~118） |

> 时间线取自 `evidence/S5-lb-healthcheck-5xx/timeline.md` 与 `app.log`。

---

## 四、根因分析（5 Whys）

1. **为什么用户大面积 502/504？** → 因为网关没有可用后端，请求无法转发。
2. **为什么没有可用后端？** → 因为 SLB 把后端判定为 DOWN 并摘除。
3. **为什么被判 DOWN？** → 因为健康检查探针 `GET /healthz` 返回 HTTP 500，连续失败超过阈值。
4. **为什么 `/healthz` 返回 500？** → 健康检查端点的返回逻辑未真实反映服务状态 / 检查路径与业务实际不符（演练中为配置错误）。
5. **为什么没有被提前发现？** → （根因层）**健康检查契约与配置未纳入变更管理与自动化校验**，且"健康检查失败"与"业务故障"未做独立告警。

**根因（可修复层）**：健康检查探针配置与后端实际状态不一致，导致后端被误摘除，而网关在无可用后端时直接返回 502/504。

---

## 五、处置过程

| 步骤 | 动作 | 效果 |
|---|---|---|
| 1. 现象确认 | 用户报"全站 502/504"；确认网关 5xx 突增、到达率骤降 | 判定"服务不可达" |
| 2. 分层分叉 | 读取后端资源指标：CPU/内存/DB/连接池全部正常 | **锁定问题在接入层**，排除业务逻辑 |
| 3. 直连验证 | 直连后端 `curl /healthz`，返回 500 | 复现健康检查失败 |
| 4. 止损 | 修正健康检查路径/端口/期望状态码；核对并恢复安全组规则 | 后端重新被判定健康 |
| 5. 恢复 | 后端恢复健康，流量回归 | 业务恢复（约 09:02:40） |
| 6. 固化 | 产出本 RCA + 新增告警规则 | 防止复发 |

---

## 六、改进项（Action Items）

| # | 改进项 | 优先级 | 验收标准 |
|---|---|---|---|
| 1 | 统一健康检查契约：`/healthz` 必须真实反映服务可用性 | 高 | 探针失败与业务故障强相关，无"业务正常但探针 500" |
| 2 | 健康检查配置纳入变更管理（配置即代码 + 二次确认） | 高 | 修改需走评审，可回滚 |
| 3 | 新增告警：网关 5xx 突增 + 到达率骤降 + SLB 后端 unhealthy 事件 | 高 | 已在 `ops/prometheus/rules.yml` 落地 |
| 4 | 健康检查失败与业务故障**分开告警**，避免混淆 | 中 | 两条独立规则，两个不同 severity |
| 5 | 把健康检查纳入发布回归用例 | 中 | 每次发布自动校验 `/healthz` |

## 八、复盘结论

- **教训**：症状在网络层、资源层却正常时，不要在业务逻辑里打转；**"网关 5xx vs 后端资源"是否一致，是决定排查方向的关键分叉**。
- **沉淀**：一条告警规则 + 一条知识库条目（见 [../tickets/知识库-KB示例.md](../tickets/知识库-KB示例.md) KB-001），使同类故障在客户报障前可被自动发现。
