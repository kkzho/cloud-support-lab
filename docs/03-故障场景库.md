> 每个场景包含：客户视角描述、现象、影响面、排障决策树、关键命令、根因、止损、修复、预防、关联云产品、工单话术，以及**本项目实测证据**。
> 所有实测数值来自 `evidence/INDEX.json` 与各场景 `summary.json`。

## S1 应用实例 CPU 打满导致接口延迟升高、部分超时

**客户视角**："我们的订单列表接口突然变得很慢，部分请求直接超时。"

**现象**
- P99 从 ~198ms 恶化到 **951ms**，出现 **13.2%** 的 5xx；
- 节点 `node_cpu_percent` 达 **97.4%**，`app_worker_busy` 升至 **17**（≈ worker 池 16 已饱和）；
- DB、缓存、磁盘指标均正常。

**影响面**：单接口性能劣化，非全站不可用；随 CPU 持续满载，延迟会进一步扩散。

**排障决策树**
```
接口变慢
├─ 网关 5xx 高？ ── 是 ── 后端资源是否也异常？
│                          ├─ 是 → 看下面各层（DB/缓存/节点）
│                          └─ 否 → 见 S5（接入层）
└─ 后端资源异常 → 节点 CPU 高？
                  ├─ 是 → 应用自身 CPU 高？(top/pidstat)
                  │        ├─ 是 → 死循环/正则回溯/加解密/序列化热点 → 抓火焰图/profiler
                  │        └─ 否 → 被同节点其他进程挤占 / CPU steal（超卖）
                  └─ 否 → 看内存(→S4)、磁盘IO、连接(→S2)
```

**关键命令**
```bash
top -H -p $(pgrep -f app)          # 定位应用内最耗 CPU 的线程
pidstat -u -p ALL 1                # 进程级 CPU
cat /proc/<pid>/status             # 线程数/上下文切换
# 压测复现：ab / wrk（本项目 Docker 版内置 loadgen 服务）
```

**根因**：应用存在 CPU 热点（本环境为请求处理路径与下游调用的计算放大），单实例 CPU 饱和后请求排队，P99 抬升并触发超时。

**止损（先恢复业务）**
1. 横向扩容（**+2 实例**）并接入 SLB，分摊流量；
2. 对非核心接口限流，保住核心链路；
3. 如伴随发布，立即回滚。

**修复**
- 用 profiler 定位热点函数，优化算法/缓存中间结果；
- 必要时升配实例，并配置**基于 CPU 的自动伸缩（HPA / 弹性伸缩）**。

**预防**
- 告警：节点/容器 CPU > 80% 持续 5 分钟；P99 > 500ms 持续 3 分钟；
- 压测常态化，建立容量基线（本项目基线：稳定态 P99 ≈ 200ms）。

**关联云产品**：ECS/CVM、ACK/TKE、弹性伸缩、SLB/CLB。

**工单话术**："已确认是应用实例 CPU 饱和导致，我们正在扩容并从接入层分摊流量，预计 X 分钟内延迟回落。"

**实测证据**：`evidence/S1-app-cpu-saturation/`

## S2 应用数据库连接池耗尽

**客户视角**："报错信息是 `Connection is not available`，业务大面积报错。"

**现象**
- `app_conn_pool_in_use = 10/10`（连接池打满），5xx 达 **20.5%**；
- 日志高频出现：`HikariPool-1 - Connection is not available, request timed out after 400ms (total=10, active=10, idle=0, waiting=36)`；
- 同时出现 `connection leak detected: 10/10 connections checked out and never returned`；
- DB 侧连接数与 CPU 正常。

**影响面**：所有依赖该库的接口大面积 5xx；但 DB 本身健康——**问题在应用侧**。

**排障决策树**
```
接口大面积 5xx + 报连接超时
├─ DB 侧指标正常？（CPU/连接数） ── 是 ── 问题在应用连接池
│     ├─ 池被占满(active==total)？
│     │     ├─ 有连接泄漏？(checked out & never returned) → 代码未在 finally 归还
│     │     └─ 无泄漏 → 慢调用占用连接太久（→ 也可能与 S3 慢SQL 叠加）
│     └─ 检查连接池参数: maximumPoolSize / connectionTimeout / leakDetectionThreshold
└─ DB 侧异常 → 见 S3
```

**关键命令**
```bash
# 应用侧
grep -c "Connection is not available" app.log
grep "connection leak detected" app.log | head
# DB 侧
mysql -e "show status like 'Threads_connected'; show processlist;"
```

**根因**：应用存在**连接泄漏**（获取连接后异常路径未归还），连接池被逐步占满，后续请求全部等待超时。

**止损**
1. **重启/滚动重启**受影响的实例，瞬间释放连接；
2. 临时**扩大连接池**（`maximumPoolSize`）并缩短 `connectionTimeout`，避免请求线程长时间阻塞；
3. 若为慢 SQL 占用连接，临时加只读实例分流读流量（与 S3 联动）。

**修复**
- 定位泄漏点：开启 `leakDetectionThreshold`，结合堆栈找到未归还连接的代码路径；
- 修复为 try-with-resources / finally 归还连接；
- 复核连接池参数：`maximumPoolSize` 与实例数 × 单实例池大小 ≤ DB 最大连接数。

**预防**
- 告警：`app_conn_pool_in_use / app_conn_pool_size > 0.8` 持续 2 分钟；
- 代码规范 + 静态扫描禁止裸获取连接；
- 上线前压测验证连接池参数。

**关联云产品**：ECS/CVM + RDS（连接数上限）、数据库代理（连接池托管）。

**工单话术**："已定位为应用连接池耗尽（存在连接未归还），我们正在重启实例并临时扩大连接池恢复业务，随后排查代码侧泄漏点。"

**实测证据**：`evidence/S2-conn-pool-exhaustion/`

## S3 慢 SQL / 缺失索引导致数据库 CPU 飙升

**客户视角**："接口整体变慢，P99 到了秒级，运维说数据库 CPU 打满。"

**现象**
- `db_cpu_percent` 从 22% 升至 **95.4%**，慢查询故障期新增 **364** 次；
- P99 从 199ms 恶化到 **2028ms**，5xx **15.7%**；
- 日志：`slow query: SELECT ... FROM orders o JOIN order_items i ON i.order_id=o.id WHERE o.status=? took 1200ms rows_examined=4427253`；
- 连接池也被拖满（慢查询长期占用连接）。

**影响面**：依赖该 DB 的**所有**接口（读多写少都会受影响）；且会连带拖垮连接池。

**排障决策树**
```
DB CPU 高 + 接口变慢 + P99 秒级
├─ 慢查询日志 / TOP SQL ？
│     ├─ 某条 SQL rows_examined 极大 → EXPLAIN 看是否走索引
│     │       ├─ type=ALL（全表扫描）/ 无命中索引 → 加索引或改写 SQL
│     │       └─ 索引被隐式转换/函数包裹失效 → 改写 WHERE 条件
│     └─ QPS 突增（非单条慢）→ 加只读实例/限流/缓存
├─ 连接数打满？ → 慢查询占连接 → 加只读实例、缩短慢查询
└─ 变更相关？（新上线接口）→ 新 SQL 引入 → 优先回滚或加索引
```

**关键命令**
```bash
# 慢查询定位
mysql -e "show variables like 'slow_query_log'; select * from mysql.slow_log order by query_time desc limit 20;"
mysql -e "EXPLAIN <慢SQL>"        # 看 type / key / rows
mysql -e "select * from sys.statements_with_full_table_scans limit 10;"  # MySQL 8.0
```

**根因**：新上线的查询走了**缺失索引的 SQL**，产生全表扫描（`rows_examined` 达百万级），DB CPU 被打满，并连带占满连接池。

**止损**
1. 识别 TOP 慢 SQL，**临时加索引**或改写（应急）；
2. 加**只读实例**分摊读流量；
3. 若为发布引入，**回滚**该变更；
4. 应用侧对重查询加**缓存/降级**。

**修复**
- 正式加索引（评估写入影响），或改写 SQL（避免回表、避免隐式转换）；
- 建立慢查询治理与上线 SQL 评审机制。

**预防**
- 告警：`db_cpu_percent > 80%` 持续 5 分钟；`db_slow_queries_total` 增速突增；
- 上线前 SQL 走审核；核心表建索引基线。

**关联云产品**：RDS/TencentDB MySQL、只读实例、数据库代理、DAS（数据库自治服务）。

**工单话术**："已定位为一条新上线查询引发全表扫描、DB CPU 打满。我们先通过加索引/只读实例止损，随后与您确认是否回滚该变更。"

**实测证据**：`evidence/S3-slow-sql-db-cpu/`

## S4 内存泄漏导致容器 OOMKilled、周期性重启

**客户视角**："服务每隔一段时间就重启一次，重启期间会有短暂报错。"

**现象**
- `node_mem_percent` 呈**锯齿状**、峰值 **99.8%**，均值 66.4%；
- `container_restarts_total` 故障期新增 **3 次**；
- 日志：`kernel: Out of memory: Killed process 8693 (java) ... container=app memory limit exceeded at 100%`、`kubelet: Container app failed with Reason OOMKilled (exit code 137); restarting container N time(s)`；
- 5xx 率很低（0.25%）——**因为重启很快、影响是间歇的**，容易被误判为"偶发"。

**影响面**：间歇性 5xx + 容量不稳定；若实例少，重启窗口内可能真不可用。

**排障决策树**
```
服务周期性重启
├─ 看容器重启次数/退出码 → exit 137 = OOMKilled（被 SELinux/内核杀）
│     ├─ 内存曲线锯齿（升到 limit 后骤降）→ 内存泄漏
│     │      ├─ 堆占用持续增长 → heap dump 分析（MAT/jmap）
│     │      └─ 堆外/直接内存增长 → 检查 NIO/Netty/缓存
│     ├─ limit 配置过小 → 结合业务实测峰值评估
│     └─ 节点整体内存不足（多容器争抢）→ 看 node_mem + 驱逐事件
└─ 非 137（如 1/143）→ 应用自身崩溃/被优雅停止
```

**关键命令**
```bash
kubectl describe pod <pod> | grep -A5 "Last State"     # 看 OOMKilled / exit 137
kubectl top pod <pod>
kubectl logs <pod> --previous                          # 上一次崩溃前的日志
dmesg | grep -i "killed process"                       # 内核 OOM 记录
# Java: jmap -histo / jmap -dump；容器内 /sys/fs/cgroup/memory
```

**根因**：应用存在内存泄漏，RSS 持续增长超过容器 limit，被内核 OOMKilled，容器反复重启形成锯齿。

**止损**
1. **临时抬高内存 limit** 或扩容，先让服务稳定，避免周期性抖动；
2. 如有多实例，先**摘除异常实例**，用健康实例承接。

**修复**
- 用 heap dump 定位泄漏对象与引用链并修复；
- 复核缓存/连接/监听器是否无上限增长。

**预防**
- 告警：`container_restarts_total` 增长；容器内存使用率 > 85% 持续 5 分钟；
- limit 依据压测峰值设定（留 30% 余量）；
- 定期做内存回归测试。

**关联云产品**：ACK/TKE、CCE、ECS/CVM、弹性伸缩（配合健康检查）。

**工单话术**："已确认服务因内存泄漏被 OOMKilled 反复重启。我们先抬高 limit 稳定服务，再排查泄漏点并给您修复计划。"

**实测证据**：`evidence/S4-memory-leak-oomkill/`

## S5 负载均衡后端健康检查失败导致 502/504（二阶问题）

**客户视角**："用户全部收到 502/504，但服务器看起来一切正常！"

**现象**
- **网关 5xx 暴增**（`gateway_upstream_5xx_total` 故障期新增 **7097**），业务接口到达率从 118 降到 **60 req/tick**（后端被摘除）；
- **后端实例资源全正常**（CPU 25%、内存 42%、DB 22%）——这就是"二阶问题"的典型特征；
- 日志：`slb: health check failed for backend 10.0.0.21:8080 GET /healthz -> HTTP 500, backend marked DOWN`、`nginx: no live upstreams while connecting to upstream, status=502`、`nginx: upstream timed out (110) ... status=504`。

**影响面**：全站不可用或大面积不可用——**这是最容易被误判、也最需要冷静的故障类型**。

**排障决策树（核心考点）**
```
用户全 5xx
├─ 后端实例资源指标是否正常？
│    ├─ 正常 ← 关键分叉！不要在应用/DB 上浪费时间
│    │     ├─ SLB 健康检查状态？→ 后端是否被标记 DOWN
│    │     │      ├─ /healthz 实际返回码？（curl 后端直连）
│    │     │      ├─ 健康检查路径/端口 配置是否与业务一致
│    │     │      └─ 健康检查间隔/阈值 是否过于严格（偶发抖动被摘）
│    │     ├─ 安全组/ACL 是否放通健康检查来源 IP 与端口？（常被"误删规则"引发）
│    │     ├─ 后端服务是否真的在监听该端口？
│    │     └─ 后端是否可被 SLB 路由到（子网/路由/VPC 一致性）
│    └─ 异常 → 回到应用层/数据层排查
```

**关键命令**
```bash
# 直连后端验证健康检查
for ip in 10.0.0.21 10.0.0.22; do curl -s -o /dev/null -w "%{http_code}\n" http://$ip:8080/healthz; done
# 查看 SLB 健康检查与后端状态（控制台/API）
# 安全组规则核对（云控制台）
```

**根因**：健康检查探针持续失败，后端被标记 DOWN 并摘除，网关因"无可用后端"返回 502/504。而**后端自身资源正常**，说明问题在**接入层/配置**，而非业务逻辑。

**止损**
1. 立即**核对并修正健康检查配置**（路径、端口、期望状态码、超时/阈值）；
2. 检查并**恢复安全组/ACL 规则**；
3. 后端 `/healthz` 修复为真实反映服务状态（避免"业务正常但健康检查 500"）。

**修复**
- 统一健康检查契约：探针路径与业务自检逻辑一致；
- 健康检查端点纳入发布回归用例。

**预防**
- 告警：`gateway_upstream_5xx_total` 突增 + 到达率骤降；SLB `backend_unhealthy` 事件；
- 禁止直接改线上安全组，走变更流程 + 二次确认；
- 健康检查失败与业务故障**分开告警**，避免混淆。

**关联云产品**：SLB/CLB/ELB、VPC 安全组、ACK/TKE（探针）、云监控。

**工单话术**："已确认是负载均衡健康检查失败导致后端被摘除，而非您的业务异常。我们正在修正健康检查/安全组配置，X 分钟内恢复。"

**实测证据**：`evidence/S5-lb-healthcheck-5xx/`

## S6 磁盘空间 / inode 打满导致写入失败、日志堆积

**客户视角**："服务突然报错 `No space left on device`，但磁盘监控看着还没满。"

**现象**
- `node_disk_percent` 峰值 **100%**、`node_inode_percent` 峰值 **100%**；5xx **15.1%**；
- 日志：`disk: write /var/log/app.log failed: No space left on device`。

**影响面**：写入类操作失败（日志、临时文件、上传、数据库落盘），可能连锁引发应用异常。

**排障决策树**
```
写入失败 / No space left on device
├─ df -h  空间是否满？
│     ├─ 是 → du 定位：日志未轮转 / 核心转储 / 临时文件 / 大文件
│     └─ 否 → df -i  inode 是否满？（大量小文件）← 最容易被忽略
│            └─ 定位目录小文件数量，清理/归档
└─ 是否有未轮转的日志随时间增长？
```

**关键命令**
```bash
df -h ; df -i                       # 空间 vs inode（两个都要看！）
du -sh /var/log/* | sort -h | tail
find / -xdev -type f -size +500M 2>/dev/null        # 大文件
find /var -xdev -type f | wc -l                     # 小文件数量
lsof | grep deleted                                 # 被删除但未释放的句柄
```

**根因**：日志未配置轮转（或轮转策略失效）导致磁盘/inode 被逐步占满，写入失败触发 5xx。

**止损**
1. 清理/归档最占空间的目录（**先确认不是业务数据**）；
2. 立即启用 `logrotate` 或清理过期日志；
3. 释放被删除但未释放的文件句柄（重启对应进程）。

**修复**
- 配置统一的日志轮转与保留策略；日志接入集中式日志（SLS/CLS/LTS）；
- 关键目录设置容量水位告警。

**预防**
- 告警：`node_disk_percent > 85%`、`node_inode_percent > 85%`（**两个都要**）；
- 定时任务巡检 + 自动清理策略。

**关联云产品**：ECS/CVM 云盘、NAS、OSS 归档、日志服务。

**工单话术**："已确认是磁盘/inode 被日志占满导致写入失败。我们先清理并启用日志轮转恢复写入，随后给出长期清理与告警方案。"

**实测证据**：`evidence/S6-disk-inode-full/`

## S7 DNS 解析异常导致间歇性 5xx / 连接超时

**客户视角**："服务时好时坏，报 `getaddrinfo failed`，看着不像机器挂了。"

**现象**
- 5xx 达 **30.1%**；P99 从 199ms 恶化到 **435ms**（间歇性）；
- 日志：`getaddrinfo failed for 'order-db.svc.cluster.local': nameserver 10.96.0.10 timeout after 340ms`。

**影响面**：间歇性 5xx —— 最让人抓狂的类型；表现为"时好时坏"。

**排障决策树**
```
间歇 5xx / 连接超时 / getaddrinfo failed
├─ 是否与依赖服务**域名解析**相关？（错误里有域名）
│     ├─ dig/nslookup 是否超时/失败？
│     │      ├─ 是 → DNS 服务器异常 / VPC DNS 配置 / CoreDNS 异常
│     │      └─ 否 → 可能是应用侧 DNS 缓存/重试策略问题
│     ├─ 是否只在高峰期发生？（并发解析把 DNS 打爆）
│     └─ 是否只影响某几个域名？（单域名解析记录异常）
└─ 与解析无关 → 回网络/连接层（安全组、路由、丢包）
```

**关键命令**
```bash
dig @<nameserver> <domain> +time=1 +tries=2
cat /etc/resolv.conf                 # 看 nameserver 与 options timeout/attempts
# K8s: kubectl get pods -n kube-system | grep coredns ; kubectl logs <coredns-pod>
nslookup <domain>
```

**根因**：DNS 解析服务异常/超时（本环境为集群 DNS `10.96.0.10` 超时），导致依赖域名解析的调用间歇性失败。

**止损**
1. 更换/增加可用 DNS（多 nameserver）；
2. 应用侧引入**本地 DNS 缓存**与**解析失败重试**；
3. 如为 CoreDNS 问题，扩容/重启 CoreDNS。

**修复**
- 修正 VPC/DNS 配置，确认解析记录正确；
- 配置合理的 `resolv.conf` 超时与重试参数；
- 核心依赖考虑**直连 IP/服务发现**降低对 DNS 的强依赖。

**预防**
- 告警：`gateway_upstream_5xx_total` 间歇性突增 + `getaddrinfo failed` 日志关键字告警；
- DNS 服务健康检查与容量监控。

**关联云产品**：VPC、私有 DNS/云解析、ACK CoreDNS、内网 DNS。

**工单话术**："已定位为 DNS 解析超时引发的间歇失败。我们正在修正 DNS 配置并增加解析重试，随后给出根因与改进项。"

**实测证据**：`evidence/S7-dns-resolution-fail/`

## S8 Redis 大 key / 热 key 导致缓存层响应抖动

**客户视角**："接口偶尔变慢，数据库压力好像也跟着涨了。"

**现象**
- `cache_latency_ms` 从 4.4ms 升至 **369ms**（近 100 倍）；
- `cache_hit_ratio` 从 0.85 降到 **0.75**（命中率下降 → 更多请求打到 DB，`db_cpu` 也升到 45%）；
- P99 从 200ms 恶化到 **629ms**，5xx **5.8%**；
- 日志：`hot key detected`、`Redis command timed out`。

**影响面**：缓存层抖动会**向上放大**为接口变慢，并**向下**把压力传导到数据库。

**排障决策树**
```
缓存层变慢 / 命中率下降
├─ Redis 单命令耗时高？
│     ├─ 大 key？（value 过大，单次取回/删除耗时长）
│     │      └─ redis-cli --bigkeys 定位；拆分大 key
│     ├─ 热 key？（单 key 高并发，单节点打满）
│     │      └─ redis-cli --hotkeys / 监控 QPS 分布；本地缓存 + 热点打散
│     └─ 实例规格/带宽瓶颈？（整体 RT 高，非单 key）
└─ 命中率下降 → 大量请求穿透到 DB → DB 压力升高（与 S3 联动）
```

**关键命令**
```bash
redis-cli -h <host> --bigkeys
redis-cli -h <host> --hotkeys
redis-cli -h <host> slowlog get 20
redis-cli -h <host> info commandstats | sort -t= -k2 -n | tail
redis-cli -h <host> --latency
```

**根因**：存在**热 key**（单个 key 承受高并发访问，打满单节点/单线程），并伴随**大 key** 导致单次操作耗时升高；缓存 RT 抖动使部分请求超时，命中率下降进一步把压力传导到数据库。

**止损**
1. 对**热 key 加本地缓存**（一级缓存）或**热点打散**（拆分为 key 后缀）；
2. 对**大 key 拆分**为多个小 key；
3. 提升 Redis 实例规格/带宽，或启用集群分片。

**修复**
- 从业务侧优化 key 设计（避免大 value、避免单点热点）；
- 建立 key 规范与容量评估。

**预防**
- 告警：`cache_latency_ms` 突增、`cache_hit_ratio < 0.7`；
- 定期 `--bigkeys` 巡检；热点 key 监控。

**关联云产品**：Tair/云 Redis、Redis 集群版、本地缓存、数据库（兜底）。

**工单话术**："已定位为缓存层热 key/大 key 导致响应抖动，并连带推高数据库压力。我们先做热点打散与本地缓存止损，随后给出 key 治理方案。"

**实测证据**：`evidence/S8-redis-hotkey/`
