# 01 架构与云产品映射

> 本文件说明演练环境的业务架构，以及它如何映射到主流公有云的产品与故障域。目的是：在面试中能把"一个具体的排障动作"翻译成"某一类云产品的某一层能力"。

---

## 一、被保障的业务：一个典型的三层电商业务

演练环境模拟的是一套被云厂商客户托管的典型业务：**接入层 → 应用层 → 数据层**，外加一层**可观测性**。

```
用户请求
   │
   ▼
[接入层]  SLB/ELB(负载均衡)  →  可选 CDN/DNS
   │            │ 健康检查探针 /healthz
   ▼            ▼
[应用层]  app 实例 × N（无状态；worker 线程池 + 连接池 + 缓存客户端）
   │                │
   │       ┌────────┴────────┐
   ▼       ▼                 ▼
[数据层] Redis(缓存)      RDS/MySQL(关系库)
   │
   ▼
[节点/基础设施]  ECS/CVM 计算节点（CPU/内存/磁盘/inode）  +  VPC 网络  +  安全组
```

关键数据流：`/api/order/list` → 先查缓存（Redis）→ 未命中则查数据库（MySQL）→ 返回。任何一个环节劣化，都会沿调用链向上放大成用户可感知的延迟或 5xx。

## 二、云产品映射（阿里云 / 腾讯云 / 华为云对照）

| 架构组件 | 阿里云 | 腾讯云 | 华为云 | 本项目仿真对象 |
|---|---|---|---|---|
| 负载均衡 | SLB / ALB | CLB | ELB | `slb`（健康检查、后端摘除） |
| 计算实例 | ECS | CVM | ECS | `app` 容器 / 节点 |
| 容器服务 | ACK | TKE | CCE | `app` 容器（OOMKilled） |
| 虚拟网络 | VPC | VPC | VPC | 安全组/路由（S7 DNS 场景） |
| 关系数据库 | RDS MySQL | TencentDB MySQL | RDS | `db`（慢查询、连接数） |
| 缓存 | Tair / Redis | 云 Redis | DCS | `cache`（大 key/热 key） |
| 对象存储 | OSS | COS | OBS | （扩展项，日志归档） |
| 监控告警 | 云监控 / ARMS | 云监控 / 可观测平台 | AOM/CES | Prometheus + Alertmanager |
| 日志 | SLS | CLS | LTS | `app.log` |

> 注意：本项目仿真的是**产品行为**，而非某一家厂商的私有实现。面试中被问到具体厂商时，把上表的"能力"对应到该厂商的具体产品即可。

## 三、故障域划分（排障定位的地图）

排障效率的本质，是**快速缩小故障域**。本项目按 5 个域划分：

| 故障域 | 典型现象 | 典型根因 | 对应场景 |
|---|---|---|---|
| **接入层** | 大量 502/504、到达率骤降、后端资源却正常 | 健康检查配置不对、安全组/ACL 误配、后端未监听 | S5 |
| **应用层** | 首响应时间正常但排队变长、连接池打满 | 连接池/线程池配置、连接泄漏、慢调用 | S1、S2 |
| **数据层** | P99 秒级、DB CPU 飙升、慢查询堆积 | 缺失索引、全表扫描、连接数打满 | S3 |
| **缓存层** | 缓存延迟抖动、命中率下降 | 大 key、热 key、单点瓶颈 | S8 |
| **节点/基础设施** | 容器反复重启、磁盘/inode 满、解析失败 | 内存超限 OOMKilled、日志未轮转、DNS 异常 | S4、S6、S7 |

**定位心法**：
1. 先看**接入层指标**（网关 5xx 率、到达率）判断"是不是全都没有请求进来"还是"请求进来了但都失败"；
2. 若网关 5xx 高但**后端资源正常** → 优先怀疑接入层配置（S5 的核心）；
3. 若后端资源异常 → 按"应用 → 数据 → 缓存 → 节点"自上而下，用**瓶颈指标**（CPU/内存/连接数/磁盘）做二分。

## 四、可观测性分层

本项目采用"指标 + 日志 + 事件"三层可观测性，与云厂商的监控体系一一对应：

| 层次 | 本项目 | 云上对应 | 用途 |
|---|---|---|---|
| 指标 (Metrics) | `evidence/*/metrics.csv`、`/metrics` 端点 | 云监控 / Prometheus | 判断"是否异常、异常多大" |
| 日志 (Logs) | `evidence/*/app.log` | SLS / CLS / LTS | 定位"异常发生在哪一层、哪一行" |
| 事件 (Events) | `summary.json` 异常信号 | kubelet events / 云事件 | 还原"什么时候发生了什么事" |

关键指标（Prometheus 口径）：
- **请求侧**：`http_requests_total{status}`、`http_request_duration_ms_p95/p99`、`gateway_upstream_5xx_total`
- **应用侧**：`app_worker_busy`、`app_conn_pool_in_use` / `app_conn_pool_size`
- **数据库**：`db_cpu_percent`、`db_connections_used` / `db_connections_max`、`db_slow_queries_total`
- **节点**：`node_cpu_percent`、`node_mem_percent`、`node_disk_percent`、`node_inode_percent`
- **缓存**：`cache_latency_ms`、`cache_hit_ratio`
- **容器**：`container_restarts_total`

## 五、高可用与部署拓扑（正确的目标形态）

演练环境的基线拓扑是"单可用区"，故障正是从这种脆弱拓扑中被放大的。生产级应达到：

- 接入层：SLB **多可用区**部署，健康检查间隔/阈值可调，后端跨可用区；
- 应用层：无状态服务 + **≥2 实例** + 自动伸缩，滚动发布；
- 数据层：RDS **主备/多可用区** + 只读实例分摊读流量；Redis 集群版；
- 节点层：容量水位红线（CPU/内存/磁盘 < 80%），日志轮转与归档；
- 变更层：灰度发布 + 快速回滚，重大变更走变更窗口。

详细的治理方案见 [04-稳定性治理方案.md](04-稳定性治理方案.md)。
